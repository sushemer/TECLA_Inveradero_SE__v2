# Protocolo ESP-NOW v3 — propuesta para revisión

**Estado:** contrato/propuesta de interoperabilidad con codec y dispatcher puros compilados en los componentes CMake activos; todavía no integrado al callback ESP-NOW ni al flujo `app_main`. Requiere revisión del coordinador y Chat6 antes de integración física. Las versiones de wire, API JSON y NVS son independientes: wire v3 no implica API schema v3 ni una migración NVS v3.

## Contrato de identidad

| Campo | Wire | Semántica |
|---|---:|---|
| `firmware_node_id` | `uint32` | Identidad técnica provisionada, distinta de `dispositivo.id` SQL, MAC y perfil compilado. Nunca inferida de `TECLA_ID_NODO`. |
| `boot_id` | 16 bytes | UUID RFC 4122 en orden de bytes de red, generado por cada arranque físico. No es UUID textual ni se guarda como string en radio. |
| `seq` | `uint32` | Little-endian, empieza en 1 y crece por nodo + `boot_id` + flujo (`msg_type`). API heartbeat valida su propio seq por node/boot; el gateway preserva el seq de cada nodo al formar `nodes[]`, no sustituye por un seq del lote. Retransmisión idéntica conserva boot/seq/payload. No wrap: nuevo arranque físico con boot distinto antes de `UINT32_MAX`; nunca se compara entre boots. |
| `command_id` | 16 bytes | UUID backend como bytes RFC 4122; solo comandos/ACK de aplicación. El gateway preserva esta identidad al retransmitir. |
| `command_config_revision` | `uint32` | Nombre canónico del contador API para el ciclo COMMAND_CONFIG (`expected`, `target`, `applied`); en el wire son campos u32 del payload. `config_revision*` se conserva como alias HTTP legacy. No versiona `MANIFEST_CONFIG` ni se cambia por su ACK. |
| `manifest_revision`, `assignment_revision` | 32 bytes cada una | API entrega 64 caracteres hex que codifican SHA-256. Gateway valida hex y decodifica a los 32 bytes raw de wire; no vuelve a hashear JSON/hex. Se guardan en el snapshot de cada muestra al capturarla y se reintentan sin recalcular. Son distintas de `command_config_revision`. |

El firmware no conoce IDs SQL (`nodo_id`, `sensor_id`, `tipo_dato_id`). El nodo reporta códigos compactos de capacidad y medición; el gateway traduce con una tabla manifest-bound `(wire_version, manifest_revision, assignment_revision, slot_code, measurement_code) → (sensor_id, tipo_dato_id, sensor_firmware_id, canal)`. `slot_code` proviene del registry estable de capacidades compiladas; código desconocido se rechaza, nunca se asigna por RSSI. `measurement_code` identifica semántica y unidad canónicas; el `slot_code` distingue sensores repetidos del mismo tipo. API v1 no manda códigos numéricos de wire, así que gateway resuelve por el registry y manifiesto determinista. Una MAC/ID ya soportada no requiere firmware nuevo; driver o capacidad nueva sí.

### Registry propuesto de capabilities (prototipo, ligado a wire v3)

Los códigos no son IDs SQL, ID de nodo, ID de inventario ni índices locales reusables. Cada `slot_code` representa una capability física estable `(sensor_firmware_id, canal)`; varias instancias del mismo tipo necesitan canales distintos. Los strings entre comillas son propuesta canónica que el manifiesto/API debe devolver exactamente. Ninguna fila decide qué sensor está instalado en un nodo real.

| `slot_code` | Capability compilada `(sensor_firmware_id, canal)` propuesta | `measurement_code` permitido | Disponibilidad en el código actual |
|---:|---|---|---|
| `0x01` | `("dht22-1", "gpio4")` | `1` Temperatura/°C; `2` Humedad/% | Driver activo; valores de registry v3 canónicos en minúsculas. VPD solo cuando se implemente cálculo validado. |
| `0x02` | `("veml7700-1", "i2c0:0x10")` | `7` Iluminancia/lux | Driver activo en perfil declarado; no implica asignación física confirmada. |
| `0x10` | `("sen0193-1", "ads1115:a0")` | `4` Humedad del sustrato/% | Capability declarada por firmware legacy, pero driver ADS1115/escala/calibración no están activos; no anunciar. |
| `0x11` | `("sen0193-2", "ads1115:a1")` | `4` Humedad del sustrato/% | Capability declarada por firmware legacy, pero driver ADS1115/escala/calibración no están activos; no anunciar. |
| `0x12` | `("sen0193-3", "ads1115:a2")` | `4` Humedad del sustrato/% | Capability declarada por firmware legacy, pero driver ADS1115/escala/calibración no están activos; no anunciar. |
| `0x13` | `("sen0193-4", "ads1115:a3")` | `4` Humedad del sustrato/% | Capability declarada por firmware legacy, pero driver ADS1115/escala/calibración no están activos; no anunciar. |

Semántica v3 del prototipo, fijando estos nombres/unidades exactos como invariantes del catálogo/API: `1 Temperatura/°C`, `2 Humedad/%`, `3 VPD/kPa`, `4 Humedad del sustrato/%`, `5 Dióxido de carbono/ppm`, `6 reservado (sin tipo PAR en seed actual)`, `7 Iluminancia/lux`. Gateway traduce `(measurement_code, tipo_dato, unidad)` contra cada medición del manifiesto; si falta o no coincide el nombre/unidad exactos, rechaza el item y pide resync, nunca deduce por ID SQL ni por nombre traducido. Los códigos 3, 5 y 6 no se anuncian por las capabilities actuales: VPD requiere cálculo firmware; SCD41 aparece en seed/demo pero no es evidencia de hardware ni driver activo; PAR no está en el seed. La API recorta espacios exteriores y conserva la cadena asignada, pero no impone minúsculas ni valida contra este registry. El gateway compara `sensor_firmware_id` y `canal` byte a byte con la forma provisionada; no normaliza mayúsculas/minúsculas. Valores históricos como `legacy-{sensor_id}` pueden no coincidir con el registry. No implica asignación real a nodos 1–3.

## Encabezado fijo

El frame es una secuencia de bytes codificada explícitamente; no se serializa directamente una estructura C `packed`. Integers son unsigned little-endian; UUID y hashes son byte arrays. `frame_len` incluye el encabezado y debe igualar los bytes recibidos.

| Offset | Bytes | Campo | Regla |
|---:|---:|---|---|
| 0 | 1 | `wire_version` | `3`; otras versiones se descartan sin reinterpretar. |
| 1 | 1 | `msg_type` | Enum cerrado abajo. |
| 2 | 2 | `frame_len` | LE; mínimo 28, máximo 250 bytes de datos ESP-NOW v1. |
| 4 | 4 | `firmware_node_id` | LE; no cero. |
| 8 | 16 | `boot_id` | UUID bytes. |
| 24 | 4 | `seq` | LE; no cero y no-wrap en el flujo del mensaje. |

**Header = 28 bytes.** Frames mal formados (versión/tipo desconocidos, longitud corta/larga, count excesivo, códigos no asignados, valores no finitos o payload truncado) se descartan; si la versión/tamaño permite una respuesta segura, enviar NACK de aplicación con motivo, si no, solo registrar contador/error. No leer campos antes de validar longitud.

## Mensajes y bytes máximos

`MAX_CAPABILITY_SLOTS=8`, `MAX_MEASUREMENTS_PER_SLOT=7`, `MAX_MEASUREMENTS_PER_FRAME=8`. `slot_code` usa códigos 1..254; cero y `0xff` son reservados. `measurement_code` v3 usa 1..7. Todo código debe estar instalado en capabilities del firmware y autorizado por el snapshot vigente. `value_f32` es IEEE-754 binary32 little-endian y debe ser finito. El gateway valida unidad y límites de instalación/fabricante con `mediciones[]` del manifiesto; el nodo solo aplica checks físicos/driver locales. Este payload no transporta límites/calibración por medición, así que no se afirma que el nodo aplique la misma validación de instalación.

Enums numéricos wire: `msg_type`: 1 CAPABILITIES, 2 HEARTBEAT, 3 TELEMETRY, 4 TELEMETRY_ACK, 5 COMMAND_CONFIG, 6 COMMAND_ACK, 7 MANIFEST_CONFIG, 8 MANIFEST_ACK. `effective_mode`: 1 OPERATIVO, 2 INACTIVO, 3 EN_MANTENIMIENTO; no incluye FALLANDO. `node_health` (solo diagnóstico local; API no lo persiste): 0 UNKNOWN, 1 OK, 2 DEGRADED, 3 LOW_BATTERY, 4 CONFIG_PENDING, 5 FAULT. `sensor_health` (solo diagnóstico local; API no lo persiste): 1 FUNCIONANDO, 2 SIN_LECTURA, 3 LECTURA_INVALIDA, 4 DESCONECTADO, 5 ERROR. `measurement_code`: 1 TEMPERATURA, 2 HUMEDAD, 3 VPD, 4 HUMEDAD_SUELO, 5 CO2, 6 reservado (sin tipo PAR en seed actual), 7 ILUMINANCIA. Mientras no haya fuente de UTC validada, `time_quality` wire solo admite 0 UNSYNCED; 1 SYNCED está reservado y el parser lo rechaza. `telemetry_ack.scope`: 1 LOCAL_VOLATILE_BUFFERED, 2 CENTRAL_COMMITTED, 3 NACK. `command_ack.stage`: 1 RECEIVED_NODE, 2 APPLIED, 3 REJECTED. `manifest_ack.stage`: 1 APPLIED, 2 REJECTED. `reason=0` significa sin rechazo; cualquier valor no cero usa tabla de códigos NACK. `enabled` y `last_command_present`: solo 0/1. `estado_admin` de sensor: 1 OPERATIVO, 2 INACTIVO, 3 EN_MANTENIMIENTO; ACTIVO legacy y RETIRADO no se transmiten.

En HEARTBEAT `boot_id`/`seq` son los del nodo y su flujo heartbeat. En TELEMETRY_ACK el header repite el boot/seq de la muestra que reconoce. En COMMAND_CONFIG el gateway solo transmite después de que el nodo anunció su boot vigente; header `boot_id` identifica ese boot objetivo y `seq` es el contador persistido de dispatch del gateway para nodo/boot/flujo de configuración. Un reintento del mismo lease conserva bytes/seq; un lease nuevo consume un dispatch_seq nuevo. En COMMAND_ACK `boot_id` es el arranque del nodo y seq es el stream de ACK del nodo; RECEIVED y resultado terminal son mensajes distintos con secuencias nuevas, retransmitir el mismo stage conserva su secuencia.

Los tamaños máximos son datos entregados a ESP-NOW, excluyen encabezados MAC y caben en el límite de 250 bytes ESP-NOW v1. Telemetría máxima: 167 B; COMMAND_CONFIG 148 B; MANIFEST_CONFIG 124 B; heartbeat 114 B; telemetry ACK 30 B; command ACK 58 B; manifest ACK 94 B; capabilities 101 B (8 slots × hasta 7 códigos de medición definidos). No fragmentar ni truncar silenciosamente v1. Un futuro soporte ESP-NOW v2 requiere negociación explícita en ambos extremos y otro presupuesto; no inferir v2 por tamaño.

Fórmulas revisables del frame máximo: telemetry `28 + (4+1+1+2+8+1+1+1+32+32) + 8×7 = 167`; COMMAND_CONFIG `28 + (16+4+4+1+2+4+1+32+32+8×3) = 148`; MANIFEST_CONFIG `28 + (1+2+4+1+32+32+8×3)=124`; heartbeat `28+4+1+1+16+32+32=114`; telemetry ACK `28+1+1=30`; command ACK `28+16+4+4+4+1+1=58`; manifest ACK `28+32+32+1+1=94`; capabilities `28+1+8×(1+1+7)=101`. Son máximos calculados de campos definidos y verificados además por el harness host aislado; todavía no son una integración radio.

## Traducción exacta hacia API v1

El radio usa códigos enumerados; gateway serializa API v1 solo con el manifiesto autenticado y la revisión guardada al capturar cada frame:

| Wire | JSON API v1 |
|---|---|
| Heartbeat header ID/boot/seq | Un elemento independiente en `POST /api/gateway/v1/heartbeat.nodes[]`: `firmware_node_id`, `boot_id` UUID canónico, `seq` de heartbeat de ese nodo, `effective_mode` string; `command_config_revision_applied` (HTTP canónico; `config_revision_applied` alias legacy); UUID de `last_applied_command_id` o `null`. Los hashes aplicados del payload se convierten a hex minúscula y se envían como par `manifest_revision_applied`/`assignment_revision_applied`; ambos cero se traducen a ambos `null`. El backend actual los persiste y GET manifest calcula UNKNOWN/CURRENT/OUT_OF_DATE. `node_health` sigue local. |
| Telemetry header/metadata | `POST /api/lecturas`: SQL `dispositivo_id` de `nodo_id` manifiesto vigente, firmware ID, boot UUID, seq, `sample_uptime_ms` entero, `time_quality:"UNSYNCED"`, sample interval. Wire v3 no ofrece UTC y el parser rechaza `SYNCED`; por tanto no incluye `captured_at` hasta acordar fuente real de tiempo. `manifest_revision`/`assignment_revision` se serializan como los 64 caracteres hex originales del snapshot; gateway no recalcula el hash al reenviar. |
| Reading `(slot_code, measurement_code, value)` | Gateway busca mapping exacto por ambas revisiones y por capability table compilada. Agrega SQL `sensor_id`, API strings `sensor_firmware_id`/`canal`, `tipo_dato_id` y `unidad` canónica del manifiesto; conserva dato original y valida finito/límites instalados. No incluye estado administrativo ni node/sensor health en `lecturas[]`. `sensor_id` y SQL type ID nunca atraviesan radio. |
| COMMAND_ACK `RECEIVED_NODE` | POST `/api/gateway/v1/commands/{command_id}/ack`, body `stage:"RECEIVED"`, `firmware_node_id`, `command_config_revision_expected` (alias `config_revision_expected` legado), `boot_id`, `seq`. |
| COMMAND_ACK `APPLIED` | Mismo endpoint con `stage:"APPLIED"` y `command_config_revision_applied` (alias `config_revision_applied` legado) igual a target guardado en la cola; target se obtiene por command_id y no se manda como campo ACK. |
| COMMAND_ACK `REJECTED` | Mismo endpoint con `stage:"REJECTED"`, correlación requerida y `message` estable `wire-v3 reason=<NAME> code=<NN>` (máx 500 chars). |
| UNKNOWN/expiración | No existe stage de radio. Gateway consulta status, verifica expiración del servidor y envía HTTP `NO_CONFIRMATION_UNKNOWN` con command_id; si no hubo ACK nodal omite boot/seq. Conserva tombstone para ACK APPLIED/REJECTED tardío por el mismo command_id. |

Un HTTP 2xx de heartbeat o telemetry no es ACK nodo. `CENTRAL_COMMITTED` del ACK radio solo sigue al 2xx de lecturas y outcomes durables aceptado/duplicado/rechazado por cada item central; datos de sensor en mantenimiento deben haberse guardado en caché local antes de reconocer el frame. La caché local de telemetría/página y ACK durable todavía no están implementados.

## Estados, ACK, deduplicación y errores

1. Al despertar, el nodo abre rendezvous; inicia radio y anuncia/manda heartbeat con boot/seq y revisiones realmente aplicadas.
2. El gateway verifica asociación explícita MAC↔`firmware_node_id` en manifiesto, revisión, config, capacidad y lease. Nunca adopta una MAC por RSSI ni transmite órdenes en broadcast.
3. Durante un rendezvous inmediato, gateway envía config/comando solo tras status→lease→dispatch confirmado, un lease/un intento lógico; gateway verifica su deadline monotónico. El nodo no evalúa vence_at/TTL porque no tiene UTC ni TTL en radio. Si no hay nodo boot vigente no despacha. La duración/timeout de rendezvous se configura aparte del sample interval.
4. MANIFEST_CONFIG/ACK es sync idempotente separado del ciclo HTTP command. Gateway solo lo envía con el manifiesto autenticado más reciente que tiene persistido; no encola una configuración de manifiesto divergente mientras offline. Hashes iguales implican no-op; si un snapshot distinto no puede verificarse como el último, conserva el aplicado y espera sync online. Los hashes no ordenan revisiones: el nodo no puede detectar por sí solo un snapshot viejo, por eso no se documenta una regla imposible de stale-ordering. El nodo valida capabilities, aplica modo/intervalos/slots y persiste ambos hashes y config de forma atómica antes de MANIFEST_ACK; un retry idéntico es idempotente. El ACK echoa los hashes exactos. En el siguiente heartbeat fresco, el nodo reporta ambos hashes aplicados; backend almacena el par y expone UNKNOWN/CURRENT/OUT_OF_DATE sin modificar `command_config_revision_applied`. MANIFEST_ACK nunca confirma/terminaliza `command_id`. Replay/autenticidad radio no se resuelven aquí; seguridad de peer/CCMP sigue pendiente y bloquea despliegue.
5. Para COMMAND_CONFIG elegible, nodo valida command ID, expected/target, capability/slots y revisiones; persiste command ID/target antes de ACK `RECEIVED_NODE`. Luego actualiza NVS y emite `APPLIED` solo con target aplicado; si falla, `REJECTED`. Gateway mapea stages HTTP: `RECEIVED_NODE`→body `stage:"RECEIVED"`; APPLIED→APPLIED; REJECTED→REJECTED. El POST API usa command_id de ruta, expected y boot/seq; gateway obtiene target desde su record, no lo inventa en el body. UNKNOWN_CONFIRMED es solo gateway→HTTP tras expiry, no un stage radio. reason→message usa tabla estable abajo. ACKs nodales y late APPLIED/REJECTED se conservan y reintentan hasta respuesta HTTP durable.
6. Nodo OPERATIVO mide por intervalo configurado. Nodo EN MANTENIMIENTO suprime todo muestreo; un sensor EN MANTENIMIENTO en nodo OPERATIVO puede seguir lectura diagnóstica. Gateway guarda esa lectura local y jamás la manda ni reintenta central. Sensor OPERATIVO en nodo OPERATIVO sí puede subirse. INACTIVO no muestrea, pero abre management rendezvous. `FALLANDO` es proyección backend por heartbeat vencido, no enum radio/admin.
7. `management_poll_interval_seconds` procede del manifiesto; gateway lo envía en MANIFEST_CONFIG y el nodo lo persiste separado de sample interval. Inicialización sin snapshot requiere commissioning/entrega de manifiesto; no inventar asignación ni intervalo por RSSI. Gateway usa valor para rendezvous/presencia/TTL; HTTP deadlines nunca se evalúan en nodo dormido.
8. Gateway traduce mapping manifest-bound. Health enums son diagnósticos locales; no se mapean a estado administrativo ni se envían en API heartbeat/lecturas actual. Para muestras mixtas, guarda sensor-maintenance local-only y manda central solo instancias operativas; frame ACK espera resultados durable por item central y cache exitoso para diagnósticos.
9. Deduplicación de telemetría: `(firmware_node_id, boot_id, flow=TELEMETRY, seq)`; retry conserva mapping/revisiones/payload. API permite batches offline fuera de orden y no aplica high-water global. Heartbeat atrasado/repetido se rechaza: gateway manda seq nuevo por nodo/boot en el siguiente rendezvous. Mapping obsoleto se pone en cuarentena, nunca se remapea.
10. Comandos son idempotentes por `command_id` + target revision; un pending activo por nodo. ACK repetido con identidad/resultado iguales es idempotente. Expirado nunca vuelve a radio sin status→lease→dispatch fresco; UNKNOWN no es stage radio. ACK terminal tardío continúa por command_id aunque UNKNOWN haya liberado FIFO, hasta cierre/HTTP 410 final.

Motivos wire cerrados: `MALFORMED_FRAME=1`, `UNKNOWN_NODE=2`, `STALE_SEQUENCE=3`, `MANIFEST_MISMATCH=4`, `ASSIGNMENT_MISMATCH=5`, `CONFIG_REVISION_MISMATCH=6`, `UNSUPPORTED_SLOT=7`, `UNSUPPORTED_MEASUREMENT=8`, `INVALID_VALUE=9`, `INVALID_STATE=10`, `CACHE_FULL=11`, `COMMAND_EXPIRED=12`, `COMMAND_ID_CONFLICT=13`, `PERSISTENCE_FAILURE=14`. `STALE_SEQUENCE` aplica a heartbeat/gestión; no se usa high-water para descartar telemetry offline fuera de orden. Versión/tipo desconocidos se descartan; no se contesta a versión desconocida. Para API REJECTED, gateway envía mensaje exactamente `wire-v3 reason=<NAME> code=<NN>` (p. ej. `wire-v3 reason=UNSUPPORTED_SLOT code=07`); en RECEIVED/APPLIED omite mensaje, y reason debe ser cero. Ningún texto libre se transmite por radio.

## Tiempo y energía

El nodo no tiene RTC/sync implementado. El dato horario inicial es `sample_uptime_ms` monotónico relativo a `boot_id` y `time_quality=UNSYNCED`; el encoder/decoder actual rechaza `SYNCED`. Gateway usa recepción UTC propia. Solo habilitar SYNCED en una versión posterior si se define y persiste fuente real de tiempo y error máximo. `captured_at` central no se inventa a partir de hora de gateway cuando hay atraso offline.

Sampling interval y `management_poll_interval_seconds` son independientes. Operativo mide y transmite; todos los modos abren rendezvous para heartbeat/config/ACK. Deep sleep apaga Wi-Fi y no recibe hasta el siguiente wake. Mientras umbral batería esté sin calibrar, el helper de política deniega deep sleep; no implica que el ciclo físico ya exista. Una ventana OTA, si algún día se autoriza, exige radio activa dentro de deadline, rollback y particiones adecuados; OTA no se implementa aquí.

## Compatibilidad y almacenamiento

Versión 2 no se reinterpreta como v3. Mixed fleet requiere un parser v2 separado y mapping/estado legacy explícito; no se mezclan sus IDs con `firmware_node_id` v3. Recomendado actualizar primero gateway y después nodos por lote, con telemetría v2/v3 etiquetada; hasta contar con ambos parsers, no declarar compatibilidad mixta.

Schema NVS es independiente del wire: cambios de protocolo no autorizan borrar NVS ni migrar command_queue. Snapshots desconocidos/corruptos deben fallar cerrado y conservar datos. Antes de la integración debe definirse migración aditiva del config NVS del nodo y persistencia de boot/config revisions/último command ACK sin guardar cada lectura en flash.

## Diferencias frente a API v1 y puntos por validar

Fuente API: `CimaInvernadero/docs/API_GATEWAY_V1.md` (checkout web, solo lectura aquí). API conserva IDs SQL y UUID textuales JSON; radio lleva firmware ID uint32, UUID byte array, códigos compactos. `sensor_id` SQL solo aparece en POST central después de traducir `slot_code + measurement_code` bajo ambas revisiones. El manifiesto v1 incluye unidades, límites opcionales de instalación/fabricante y estado/referencia de calibración; el gateway/nodo deben validar contra ese metadata, sin inventar valores ni transformar la muestra.

Chat6 aprobó códigos compactos, sync manifest hash-only y persistencia/heartbeat de hashes aplicados. La tabla v3 propone slots para los drivers/capabilities conocidos; SEN0193 sigue no disponible por falta del driver ADS1115 y SCD41 no se incorpora por estar solo en seed/demo. Los nombres/unidades de catálogo se fijan como invariantes del prototipo y deben revisarse si cambian. El codec bytewise ofrece builders/parsers tipados para los ocho mensajes; las pruebas host existentes cubren roundtrip, payload COMMAND_ACK byte-exacto y malformed/version/size/límite. Los componentes CMake activos de nodo y gateway ahora incluyen el codec puro; el componente gateway también incluye `gateway_dispatch.c`. El dispatcher host-testable acepta solo pares explícitos firmware_node_id+MAC, copia frames TELEMETRY completos a una FIFO volátil de 8 antes de emitir `LOCAL_VOLATILE_BUFFERED`, re-ACKea duplicados idénticos y rechaza una misma identidad con bytes distintos. `peek_head`/`ack_head` permiten al consumidor liberar FIFO solo tras confirmar manejo durable; no hay consumidor conectado hoy. El harness `radio_dispatch_test.c` cubre encode→dispatch→ACK app correlacionado con mock radio, MAC no asignada, duplicado conflictivo válido, full/NACK, orden FIFO y reutilización tras pop. El harness radio dispatch pasó GCC `-std=c11 -Wall -Wextra -Werror -fsyntax-only`; su runtime quedó sin ejecutar cuando Windows pidió elevación. El nuevo harness CLI de identidad sí pasó runtime host por DLL cargada en proceso x86. Esto no es integración radio ni evidencia física: `app_main` y callbacks activos siguen usando la ruta existente y no invocan v3. La NVS de `firmware_node_id` y el fail-closed existen; el parser/procesador de CLI es host-only y falta consola física, build ESP-IDF, migración de configuración NVS, caché/página local de telemetría maintenance, callback ESP-NOW v3, persistencia de FIFO, política de replay/CCMP y mixed v2. Ningún nuevo ID físico o asignación de nodos 1–3 queda decidido por este documento.

Base ESP-NOW: ESP-IDF v5.5 limita datos ESP-NOW v1 a 250 bytes; v2 permite frames mayores solo con condiciones de compatibilidad. Su callback de recepción corre en Wi-Fi task y debe copiar metadata a cola de menor prioridad. Ver [guía oficial ESP-NOW v5.5](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/network/esp_now.html).
